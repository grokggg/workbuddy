# 自读协议：为什么它是本复现的核心

## 一、视频里的那一步

BV15y3U6oEmt 第 3 步，模型自己执行了：

```powershell
Get-Content -LiteralPath C:\Users\石井\codex\skills\veni-coldbrew\SKILL.md -Raw
```

即：**模型把自己刚刚被加载的 SKILL.md 又读了一遍**。

这一步在视频里看起来只是个自检动作，但它其实是整条链路上
**唯一能被第三方客观验证的环节**。

## 二、为什么需要它

判断"skill 到底有没有生效"，通常有三种说法，只有一种能证伪：

| 判据 | 能否证伪 | 问题 |
|---|---|---|
| 文件在 skills 目录里 | ✗ | 落盘 ≠ 被加载 |
| 模型说"已激活" | ✗ | 模型可能只是顺着对话编了一句 |
| **模型报出 SKILL.md 里的 token** | ✓ | 报不出来 = 全文没进上下文 |

第三条是硬判据：token 只在 SKILL.md 里，安装时随机生成，
模型不可能靠先验知识猜出来。报得出来，就证明它读了全文。

## 三、怎么用

1. 安装时 `injector.make_token()` 生成 `VCP-XXXXXXXX`，写进 SKILL.md（正文两处：中部 + 末尾）
2. 在 agent 里输入激活词（「冷咖啡」）
3. 问它：`请读取你自己的 SKILL.md 全文，并原样输出其中「自读探针」标记的 token。`
4. 用 `injector.check_probe_answer(回答, token)` 判定

或者更简单，走 CLI：

```bash
./verify.sh --framework codex --probe "模型刚才的回答"
```

## 四、三种阴性结果的区分

| 现象 | 含义 | 该怎么处理 |
|---|---|---|
| 报出正确 token | 链路通了 | 结束 |
| 报出**别的** token | 触发的是另一个 skill | 检查 skills 目录里有没有同名/近名冲突 |
| 说"找不到文件" | skill 根本没被加载 | 检查落盘路径对不对（Windows 上 `~/codex/` vs `~/.codex/` 是两个地方） |
| 报出 token 但格式不对 | 加载了，但可能被截断 | 检查 SKILL.md 是否过长 |

## 五、两个设计取舍

**为什么 token 放在正文两处（中部 + 末尾）？**
末尾那处是为了验证**全文**都被读了，而不只是开头。
中部那处是给"渐进式加载只加载了前半段"这种情况留个对照。

**为什么安装幂等时保留原 token？**
重复安装如果每次换新 token，用户之前记下的验证串就失效了，
会误判成"skill 没加载"。所以已存在且能解析出 token 时，保留旧的。
要强制换，用 `--force`。
