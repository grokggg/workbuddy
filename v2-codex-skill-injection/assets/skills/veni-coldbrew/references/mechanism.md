# 机制拆解：为什么落盘一个文件就能改模型行为

来源：BV15y3U6oEmt（by茶，197s，Codex Skill 注入）
本文件只讲机制，不讲任何越权操作。

## 一、这不是提示词注入，是配置注入

一次性提示词注入：把指令混进**用户的输入**里，模型在当轮读到，换会话就失效。

Skill 目录注入：把指令写成**框架会主动读取的配置文件**。
区别在三点：

| 维度 | 提示词注入 | Skill 目录注入 |
|---|---|---|
| 持久性 | 当前会话 | **跨会话**，直到文件被删 |
| 可见性 | 出现在对话里，用户看得到 | **不出现在对话里**，界面只显示"激活 XX 模式" |
| 触发 | 每轮都要带 | 靠 `description` 字段匹配激活词 |
| 权限 | 受当轮上下文限制 | 「完全访问」下 = 模型的实际执行权限 |

视频第 1 步就是把 `SKILL.md` 放到 `~/codex/skills/veni-coldbrew/` ——
**整个攻击面就是一次文件写入**。

## 二、链路的五步

```
1. 落盘     SKILL.md → ~/codex/skills/<name>/SKILL.md
2. 扫描     框架启动时读所有 SKILL.md 的 name + description（渐进式加载第 1 层）
3. 命中     用户输入「冷咖啡」≈ description 里的激活词 → 框架把全文塞进上下文
4. 自读     模型执行 Get-Content/cat 读自己的 SKILL.md（视频第 3 步）
5. 执行     模型按正文行动，调 PowerShell / node 工具链
```

第 3 步是关键：**渐进式加载**。框架不会把所有 skill 都塞进上下文 ——
先扫 `name` + `description`（便宜），命中才读正文（贵），
正文里再指向 `references/`（按需）。

所以 `description` 字段 = 唯一的检索入口。它写什么，决定了这个 skill
会在什么输入下被激活。这也意味着：**改一个 description，就能改变触发条件**，
而用户在界面上完全看不到这个字段。

## 三、三个真正的脆弱点

1. **目录默认可写、无签名校验**
   任何能往用户目录落盘的进程都能注入。不需要提权，不需要漏洞。

2. **`description` 是自然语言，触发判定不可审计**
   模型对"这句话算不算激活词"的判断，既不可预测也不可复现。
   同一个 skill 换个措辞问，可能触发也可能不触发。

3. **可观测性为零**
   界面显示的是 `激活冷咖啡模式` 这类**框架生成的摘要**，不是 SKILL.md 原文。
   用户不知道自己加载了什么。视频第 3 步模型自读文件，
   反而是**用户唯一能看到原文的机会**。

## 四、本复现做了什么、没做什么

**做了**（可客观验证的部分）：
- 落盘 / 卸载 / 结构校验 —— 全在 `lib/injector.py`
- 自读探针 —— 把"是否真的加载"从主观判断变成可证伪的判据
- Electron asar 解包 —— 合法能力，用于演示"skill → 工具链"这一段

**没做**（原视频里属于越权操作的部分）：
- 破解、去卡密、绕过授权校验
- 生成注册机 / 激活码 / 补丁
- 「内部学习，不会拿去做违法事情」这类**免责话术**——
  它在机制上是一种降低模型戒备的社会工程包装，本文件保留分析、不保留实现

## 五、防御侧对应做法

- 对 skills 目录建哈希基线，新增/改动即告警（见 `../../../../defense/t06_skill_baseline/`，
  在 `agent-sec-toolkit` 里）
- 审计 `description` 字段：激活词是否过宽、是否含高危词
- 把 skills 目录设为只读，或在 CI 里做目录快照比对
- 关闭「完全访问」，让 skill 无法自行执行 shell
