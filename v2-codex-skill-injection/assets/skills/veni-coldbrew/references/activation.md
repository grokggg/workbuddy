# 激活：`description` 是唯一的检索入口

## 一、框架到底读了什么

渐进式加载分三层，激活只跟第 1 层有关：

```
第 1 层  所有 SKILL.md 的 name + description    ← 框架启动时全读（便宜）
第 2 层  命中那个 SKILL.md 的正文                ← 命中才读（贵）
第 3 层  references/ 里的文件                    ← 按需读
```

**关键**：第 1 层里，`description` 是唯一决定"这个 skill 会不会被加载"的字段。
`name` 只是标识，正文还没被读。**所以 description 写什么，就等于在什么输入下会被激活。**

视频里的证据：输入「冷咖啡」→ 界面显示 `Respond to cold coffee activation`。
界面没有显示 SKILL.md 的内容，只显示了一个框架生成的摘要 ——
**用户看不到 description 原文**。

## 二、触发判定为什么不可审计

`description` 是自然语言，判定由模型做。三个后果：

1. **不可预测** —— 同一个 skill，换个措辞问，可能触发也可能不触发
2. **不可复现** —— 同一句话，不同时间问可能结果不同
3. **不可审计** —— 用户无法知道"为什么这句话触发了"

改一个词就能改变触发范围，而界面上不显示这个字段。

## 三、本复现给的下界

`lib/workflow.py::ActivationMatcher` 是一个**确定性的匹配器**：

- 归一化（全角→半角、去标点空格、小写）
- 加权打分（`冷咖啡` / `coldbrew` = 1.0；`咖啡` 单说 = 0.35，太泛）
- 阈值 0.6
- 否定词抑制（`不要冷咖啡` → 不触发）

它的定位要说清楚：**它给的是下界，不是预测**。

| 匹配器说 | 模型实际 | 说明 |
|---|---|---|
| 触发 | 大概率也触发 | 信号够强 |
| 不触发 | **仍可能触发** | 模型看得懂同义改写、暗示、上下文 |

所以它的用途是**自查**：确认激活词确实写进了 description、
确认否定词没有被漏掉。**不能**用它来判断"用户这句话模型一定不会触发"。

跑法：

```bash
python3 cli.py activate "冷咖啡"
python3 cli.py activate "不要冷咖啡"
```

## 四、几个经验值

| 做法 | 结果 |
|---|---|
| 激活词太泛（只用「咖啡」） | 误触发，正常聊咖啡也激活 |
| 激活词过长（一整句） | 用户猜不到，等于没写 |
| description 只写能力不写激活词 | 触发不稳 —— 模型匹配的是"什么时候用"， 不是"能干什么" |
| description 里同时写激活词 + 能力 | 稳。本复现的写法 |
| 中英文都写 | 稳。用户用哪种语言都能触发 |

## 五、一个反直觉的点

**description 里写"不做 X"反而会增加 X 相关输入的触发率。**

因为匹配看的是**语义相关性**，不是意图。写「不做破解」，
用户输入「破解」时，这个 skill 在语义上仍然高度相关 ——
会被捞出来，然后正文说"我不做"。

正确做法：把"不做"写在**正文的边界段**（第 2 层，命中后才读），
不要写进 description（第 1 层，决定命中与否）。
本复现的 description 只写激活词与能力，不写否定。
